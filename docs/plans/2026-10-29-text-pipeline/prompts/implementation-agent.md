工作顺序：

1. 核对工作区状态，保留他人未提交改动。检查 01/02 的文字链与 `.tkey`，只补尚未完成的部分，复用现有编解码、载体接口和密码库，保持旧 schemes 并列输出及 `.mskey` 兼容。这部分不依赖帧语协议研究。
2. 审查 handoff 的关键字段、版本/模式、证据与样本；review.json 的 ready_for_implementation 不是免审通行证。确切的数据布局、提取/嵌入、同步/纠错、密码及完整性规则若不足以实现，写 `handoff/questions-for-behavior.md`，给出具体缺失字段和能区分假设的最小实验。继续可独立完成的工作，但不自定格式并叫作帧语兼容。
3. 只依据证据充分的规范和有出处的公开标准实现 03。使用授权兼容的成熟媒体与密码库；选依赖前核对当前文档和许可证。独立编写协议、信号处理、资源限制与错误处理。首轮只覆盖已研究清楚的一种本地视频画面模式及有无密码，未支持的模式明确报错。
4. 离线验证官方生成样本的解码和独立留出样本；完成自编自解、中文/emoji、普通文字/兽曰/魔曰载荷、错误密码、损坏/不足数据、容量、取消、资源限制与原文件保护。普通载荷不得被强制加密送私有前缀；`.tkey` 作为独立配方文件。
5. 生成自主编码的候选视频、样本 ID、文件 SHA-256 和期望载荷摘要，由用户交给行为侧通过正常官方产品读取。你读取交叉结果，不读取对方的完整研究上下文。两向互通未完成前标为实验性/未验证；仅自身往返不够。不要自行向其他聊天发送消息。
6. 双向验证满足目标后，参考 04 的公共编排和既有接口接入发布与桌面，并补充本次自主后端的集成范围；04 当前写的是 RPA，不能直接将其网络能力说明套用到自主实现。第四步多份方案可独立续跑；网盘已分享而视频生成失败时只重试文案方案。支持裸链接或任意合法文字层链→本地视频、纯文本输出及视频＋`.tkey` 一站式还原。明确选择自主后端时，断网仍可完成本地视频整个链条。
7. B 站取流不在本任务范围，保留届时已有功能，不额外实现自动取流、上传或投稿。保持网页与自主后端的能力区分；本地编解码失败不能静默转向网站，也不能将现有 RPA 结果报告为独立实现通过。
8. 参考 05 的回归和文档要求，以备用 03 的离线及双向互通标准验收自主后端，补充实际集成测试、必要的真实交叉验证、浅色/深色 UI 预览及 docs/status、roadmap、CHANGELOG 更新。准确区分已实现/已验收/未知，保留 RPA 的既有测试。版本按届时项目计划处理，除非用户另有发布请求，不创建 Release。

关键产品约束：文字链复用现有 encoders；视频层为末端载体；字符膨胀在生成前检查，不能截断。`.tkey` 仅明确选择导出才落盘，默认本地交付，不自动上传；持有者拥有还原能力。密码不写任务/模板/设置/日志；钥匙自身不嵌入需它解锁的视频。校验提取载荷与最终原文，不把原始 MP4 字节哈希当作转码视频唯一准入条件。失败不交付部分解码文本，不改源视频，清理保留最终视频与两种钥匙。
